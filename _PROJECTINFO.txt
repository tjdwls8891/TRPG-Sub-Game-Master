v5.33.0 · SCHEMA_VERSION 3 · 7-WP 리팩터링(WP-A~G) 반영 · 2026-09-30 갱신
==============================================================
Gemini API + discord.py 기반 한국어 TRPG 보조 GM 디스코드 봇.
플레이어는 서버 GM 스페이스의 버튼으로 세션을 열고, 캐릭터를 만들고,
게임 채널에 행동을 선언한다. AI가 4개 층위(판단·지시·묘사·추출)로
턴을 진행한다. 명령어는 GM의 수동 개입·복구 수단이며 일반 플레이에는
쓰지 않는다.

> 상세·최신 설명의 정본은 CLAUDE.md. 설계 이유·이력은 DEVLOG.md.
> 이 문서는 빠른 온보딩 요약이다. 수치는 tools/verify_docs.py로 대조한다.
> (v1.9 시절 이 문서의 !진행 태그·!수정·!재생성 롤백·압축 선결제 설명은
>  모두 폐기됐다. 과거 설명이 필요하면 git 이력을 본다.)

2. 턴 흐름
==============================================================
플레이어 선언(게임 채널)
 → TurnTransaction 시작(자동 논리 턴 1개 = 트랜잭션 1개. 재시도는 새 시도 아님)
 → [판단층위] ASK / NARRATE / ROLL / PROCEED — 캐시를 읽지 않는다
 → [개연성 시뮬레이션] → [지시층위] 묘사 지시문 + 퀘스트 선택(캐시 읽음)
 → [묘사층위] 스트리밍 송출과 동시에 [추출층위] 실행
 → 모든 결과는 TurnPreparation에 스테이징(정본 미변경)
 → 필수 작업 합류 → READY_TO_COMMIT
 → CommitCoordinator가 정본 적용 + strict 저장 + CommitJournal + Settlement 청구
 → 커밋 이후에만 파생 알림 송출, 다음 라운드 개방

실패한 턴은 FAILED_SYSTEM으로 정산되고 플레이어 청구는 0이다(provider 비용은 사실로 남음).
추출 결과의 정본 적용 경로는 CommitCoordinator → _apply_commit_effects →
_apply_prepared_extraction → _apply_extraction_plan 하나뿐이다. 준비 객체 없이
_run_extraction을 부르면 provider 호출 전에 거부된다.

공유 묘사 엔진 GameCog._execute_proceed의 호출자는 자동 턴(_dispatch_proceed)과
인트로(play_intro) 둘뿐이다(수동 !진행·!수정은 WP-G에서 은퇴).

3. 핵심 권위와 패턴
==============================================================
[A] 재무 권위 3분할
  provider 사용량·비용  → CostLedger(data/cost_ledger.jsonl, append-only,
                          기록 당시 KRW/USD). strict 조회는 list_cost_events_strict.
  정상 턴 플레이어 부담 → Settlement → InkTransaction(정확히 한 번, 계정 마커)
  캐시 창 선불·환급      → cache_lifecycle 저널 + LifecycleInkTransaction
  유지 시간 해석 청구    → interpretation_billing 저널(strict CostEvent 이후에만)
  total_cost / total_usd / turn_cost_log 는 표시용 호환 미러. 규칙 입력 금지.
  둘은 집계 범위가 달라(무료 프로필 AI는 usd에만) 환율 등식으로 잇지 않는다.
  자동 GM 비용 상한 = CostLedger 세션 합계 − 활성화 스냅샷(fail-closed).
  압축 provider 비용 = 운영자 부담 유지비(선결제 개념 없음).

[B] 되감기·재생성 (turn_history)
  커밋된 턴마다 전후 상태를 기록하고 "선택"을 바꾼다. !되감기·disp:rewind*.
  !재생성 = 같은 논리 턴의 새 시도(rerender_latest). 새 시도가 COMMITTED된
  뒤에만 선택이 넘어가며, 기존 청구는 유지되고 실패한 재생성은 청구 0.
  재무 사실은 되감지 않는다.

[C] 프롬프트 권위 (WP-G D1, 정보 종류별)
  플레이어 주권: PC 행위에 대한 최상위 제약
  룰북 고정 사실·금지사항: note·GM 지시로 무효화 불가
  런타임 상태: 변하는 항목(NPC 현재 위치·상태)만 초기값보다 우선
  session.note·캐시 노트: 추가·범위 축소. 충돌 시 자동 override 안 함
  GM 지시·[진행자] 중계·사이드 노트: 위 범위 안의 진행 지시
  압축 기억: 파생 기억 / 플레이어의 외부 세계 주장: 미확인 주장
  자원·상태 변화: 묘사 → 추출 → 코드 검증으로만 적용. 자:/태: 태그는 권위 없음
  (방어적 strip만), 상:/중:/하: 장소 이미지 태그는 유지.

[D] 캐시 룰북 조립 (core/cache.py)
  [1]세계관 → [1-B]연고지 상세(keyword_memory) → [2]스토리 가이드 → [3]NPC 사전
  → [4]스탯·판정 → [4.5]상태이상 목록 → [5]묘사 가이드 → [6]금지사항
  → [7]상태창 양식 → [8]세션 추가 NPC → [9]압축 기억 → 캐시 노트
  → GM 의사결정 엔진 전용 지시문(묘사 시 무시하도록 라벨)
  → MIN_CACHE_TOKENS(기본 1024) 미달 시 패딩.
  캐시 생성·교체·삭제·보관비는 cache_lifecycle 단일 finalizer를 거친다.

[E] 기억 압축 (memory_plan)
  플랜별 주기(노멀 5 / 하이 3 / 로우 5 / 울트라 1). 백그라운드 실행.
  출발 시점의 출처 식별(세대·접두 지문)이 여전히 정본일 때만 적용하고,
  아니면 결과를 폐기한다(비용은 사실로 남음). 적용된 모든 압축이
  last_compressed_turn·compression_count를 갱신한다.

[F] 메시지 생애주기 (message_lifecycle)
  CANONICAL_DISPLAY / INTERACTION_PROMPT / TRANSIENT_GAME_STATUS /
  CANONICAL_GAME_EVENT / OPERATOR_LOG. 대기 안내 등 임시 메시지는
  성공·실패·취소 어느 경로든 정리된다. 운영 로그는 플레이어 채널로 새지 않는다.

[G] 오디오 (audio_mixer · tts)
  BGM/플리 + 효과음 + 음성을 20ms 프레임마다 합산(덕킹). TTS 더빙은
  인트로 묘사에만 적용된다(자동 턴 미적용).

8. 개발 주의사항
==============================================================
- 커밋 전 CLAUDE.md의 검증 루틴 ①~④(+⑤ 봇 로딩)을 돌린다.
  기준값: cogs 9 · 명령어 44 · views 5.
- prompts.py·scenarios/*.json은 수정안 → 승인 → 적용. 변경 후 운영에서 !캐시 재발급.
- 권위 불변식 테스트가 실패하면 테스트를 완화하지 말고 설계를 맞춘다
  (예: strict 세션 저장은 commit_coordinator에만).
- 정본 상태를 바꾸는 새 경로를 만들지 않는다. 턴 결과는 준비 → READY → 커밋.
